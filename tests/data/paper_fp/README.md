# Paper false-positive scenarios — `tests/data/paper_fp/`

**Replications** of the three false-positive scenarios studied in:

> Sangjun Lee, Jungheum Park, Sangjin Lee & Doowon Choi, *"A study on the false
> positives of existing tools for recovering deleted records in SQLite
> databases"*, Forensic Science International: Digital Investigation **55**
> (2025), article 302031.
> DOI: [10.1016/j.fsidi.2025.302031](https://doi.org/10.1016/j.fsidi.2025.302031)

## What these are — and what they are NOT

These three databases REPLICATE the *construction* of the paper's Table 5
scenarios, built with the real `sqlite3` engine via Python's stdlib `sqlite3`
module (see [`gen.py`](gen.py)). They are **not** the paper's official corpus.

> **Provenance honesty.** The paper's own extended corpus + code is, per its
> data-availability statement, "released upon publication". At authoring time no
> public URL exists for it (it is not in the article, supplementary material, or
> a linked repository, and is not otherwise findable). We therefore reproduce the
> *scenario construction* the paper documents — not its bytes. Every number this
> repo measures against these files is labelled **"measured (this repo, identical
> bytes)"**; numbers attributed to the paper's own corpus are labelled
> **"reported by the paper"** and are never conflated. **Track for swap-in:** when
> the official corpus is released, replace these fixtures with it and re-measure.

## The scenarios (paper Table 5 taxonomy)

The paper classifies two false-positive classes that existing carvers mishandle:

- **Type \*\*  — B-tree rebalancing.** A range DELETE triggers interior-node
  merges; freed pages keep their payload, and a *live* row that a rebalance moved
  onto a freed page is mis-reported as deleted by carvers that scan freed pages
  without excluding live rowids.
- **Type \*  — table reinsertion, same schema.** A table is DROPped and
  re-CREATEd with the *same* schema; residual rows from the dropped table can be
  mis-attributed to the recreated same-name table.

| File | Scenario | `secure_delete` | Construction | Ground truth |
|---|---|---|---|---|
| `f.db` | **0F** — B-tree rebalancing (Type \*\*) | OFF | `t(id INTEGER PRIMARY KEY, v TEXT)`; insert ids 1..80 with a ~420-byte id-tagged `v`; `DELETE WHERE id BETWEEN 1 AND 50` | live ids **51..80** (30 rows); deleted ids **1..50**; `freelist_count = 5` |
| `b.db` | **0B** — overwritten table, same schema (Type \*) | OFF | `students(id INTEGER PRIMARY KEY, name, affil)`; insert 10 `OLD-NAME-i`; `DROP TABLE`; recreate SAME schema; insert 5 `NEW-NAME-i` | live ids **1..5** (`NEW-NAME`); dropped residue = **10 `OLD-NAME` rows** |
| `wcase.db` + `wcase.db-wal` | **10** — WAL + `secure_delete=ON` | ON | WAL mode, `wal_autocheckpoint=0`; insert 20 `SECRET-MESSAGE-i` (NOT checkpointed); a 2nd reader pins the WAL; `DELETE WHERE id BETWEEN 1 AND 20`; copy db + `-wal` while open | live **0**; deleted ids **1..20**; residue **only in `-wal`** (main image holds zero message bodies) |

### Design note — id-tagged payloads (0F)

`f.db`'s `v` embeds the row id (`ROW-<id>-XXXX…`, ~420 bytes). The id-alias
(`INTEGER PRIMARY KEY`) is stored as a header rowid, which content-keyed tools
that drop the rowid (bring2lite and SQL-DRP both emit a `NULL` rowid-alias cell)
cannot recover — so the embedded tag is what lets every tool's output be scored
against the live/deleted sets. Without it, an all-identical payload would make a
Type-\*\* false positive (a *live* 51..80 row surfaced from a freed page)
indistinguishable from a true deleted recovery.

## md5 manifest

Regenerate with `python3 gen.py`. The main-image databases are byte-reproducible
on the same engine; the **`-wal` is not** — SQLite writes random salt + checksum
values into the WAL header per run, so `wcase.db-wal`'s md5 changes each
regeneration while its recoverable content (20 `SECRET-MESSAGE` frames) does not.
